# Mobula UI — UI/UX Requirements & Design Specification

**Status:** Draft v0.2 (planning document — no implementation yet). Re-baselined 2026-08-15 against `mobula` @ `d9fd64f` (Phase 3 complete + Phase 4 slice 1) **plus the uncommitted working tree** (Ray Serve service API — flagged inline where cited); the canonical API contract is now [`mobula/docs/api-v1.md`](../../mobula/docs/api-v1.md) (DRAFT) — §8 below is a summary of it, not the source of truth.
**Repo:** `mobula-ui` · **Backend:** [`mobula`](../mobula) (Rust control plane for Ray)
**Mission:** A self-hosted, FOSS replacement for the Anyscale console — the single source of truth for configuring and operating Ray hardware (clusters, nodes, worker groups) and workloads.

## 1. Mission & Non-Goals

### 1.1 What this product is

Mobula UI is the management console for the Mobula control plane. It is where operators **define** hardware (clusters, worker groups, autoscaling bounds, registry endpoints) and where developers **consume** it (submit jobs, tail logs, inspect cluster state). Anything Anyscale's console does for Ray fleets, this aims to do as open source.

### 1.2 Critical ground truth: where Mobula is today

Re-baselined 2026-08-15 against `mobula` @ `d9fd64f`. Mobula has finished **Phases 1–3 and Phase 4 slice 1**. What exists in code:

- A **federating Ray Jobs gateway**: host-based routing (`Host` header → registered cluster's Ray Jobs API at `:8265`), with credential swap (caller's JWT terminates at Mobula; the cluster's static Ray token travels southbound), including the websocket log-tail bridge.
- A complete **OIDC/RBAC layer**: RS256 JWT validation, **four roles as permission-sets** (`Viewer, Developer, Operator, Admin` over `(verb, target)` grants — see §2 and ADR-0009), deny-by-default middleware, device-code + client-credentials CLI flows, Envoy `ext_authz` check endpoint (`/api/v1/authz/check`).
- A **cluster lifecycle controller** (`mobula-controller` + `mobula-provision`): `Store` trait with in-memory and **SQLite** impls (`store.rs`, `store_sqlite.rs` — SQL written to port to Postgres unchanged, but no Postgres store yet), an observation-first reconcile engine (ADR-0006/0007) with derived idempotency keys (`{cluster_uid}/{spec_generation}`), a resync loop + **max-age TTL reaping** wired into `serve --kuberay-namespace`, and a **live KubeRay provisioner** over kube-rs (server-side apply, kind e2e green).
- **Cluster CRUD API** (`mobula-api/src/clusters.rs`): `GET/POST /api/v1/clusters`, `GET/DELETE /api/v1/clusters/{id}`, with per-route permission checks and **quota admission on create** (409 `quota_exceeded`; `mobula-policy` — Phase 4 slice 1). `ClusterView` carries `est_min_hourly`/`est_max_hourly` when a price sheet is configured.
- **Ray Serve service API** (`mobula-api/src/services.rs`) — **in the working tree, not yet committed**: `GET/POST /api/v1/services`, `GET/DELETE /api/v1/services/{name}`, a thin authenticated CRUD proxy over KubeRay `RayService` (no Mobula store/reconcile — the RayService controller owns convergence and canary upgrades; `ServiceSpec.serve_config_v2` passes through verbatim, `upgrade` defaults to canary). Adds a third RBAC target: `Target::Service` (deploy = "code", so Developer writes, Operator reads).
- The **domain model**: `ClusterSpec`, `WorkerGroup`, `ClusterState` (9-state machine), `ClusterRegistry` (static TOML file).
- Swagger UI at `/docs`, OpenAPI at `/api/v1/openapi.json`, and a **committed `openapi.json` at the mobula repo root** regenerated by `cargo test -p mobula-api export_openapi` (commit `0c5a3e4`) — the UI vendors this file for TypeScript codegen.

What does **not** exist yet: `PATCH /clusters/{id}`, suspend/resume/terminate action endpoints (`DesiredState` is only `Running | Terminated`; DELETE is terminate), a Postgres store, Postgres-backed audit and job-history records (audit is still JSONL), the path-based jobs proxy and nodes endpoint for the browser, registry read/write APIs, the identity/who-am-I endpoint, PKCE browser login, Prometheus metrics, SSE events, and any web UI beyond Swagger.

> **Consequence (revised):** The UI no longer defines the management API from scratch — much of it **exists and is documented**. The canonical contract is `mobula/docs/api-v1.md` (DRAFT proposal, grounded in the code); §8 of this document is now a status summary pointing at it. Where a screen's backing is missing, api-v1.md already specifies it (Milestones A–C); where the spec and the code genuinely conflict, §10 records an open question. Every screen spec below still states whether its backing is *implemented*, *specced (api-v1.md)*, or *greenfield*.

### 1.3 Non-goals (v1)

Following Mobula's own v0 cut line (`PLAN.md`): no VM/static cloud provisioners, no deep Ray Serve UX (a thin authenticated Serve CRUD *API* is landing — §1.2 — but canary/rollback dashboards and Serve-app observability screens are Phase 4), no cost dashboards/billing UI (per-cluster $/hr *estimates* from the backend's price sheet are surfaced — they're already on the wire), no SCIM, no workspaces, no fair-share scheduling, no HA console. No multi-tenancy *inside* a cluster — the isolation boundary is the cluster.

### 1.4 UX principles

1. **State-machine fidelity.** The UI never invents cluster states. Every badge, action button, and transition maps 1:1 to `ClusterState` (`mobula-core/src/cluster.rs:52`): `Pending, Provisioning, Running, Degraded, Updating, Suspending, Suspended, Terminating, Terminated`. Illegal actions are hidden or disabled with an explanation, never just absent.
2. **Declarative in, observed out.** Desired state (what the user edits) and observed state (what the provisioner reports via `Provisioner::observe()`) are visually distinct everywhere they coexist. Never let a user confuse "I asked for 4 replicas" with "4 replicas exist."
3. **Secrets are write-only.** Cluster `auth_token`s are never serialized out of the backend (`registry.rs:21`). The UI shows a masked "token is set" indicator and a rotate/replace field — never a reveal button.
4. **Role-shaped UI.** The interface renders from the caller's held **role set** (`Identity.roles`, union semantics — `Identity::permits` is an `any` over held roles), not from feature flags and not from an ordinal rank: `Operator` and `Developer` overlap without containing each other, so the UI must ask "does any held role grant `Write` on `Cluster`?" rather than "is the user at least Developer?". Viewers see a read-only console; Operator-only surfaces (cluster create/lifecycle) and Admin-only surfaces (registry, access, audit) render exactly when the caller's grants permit them.
5. **Gateway discipline.** Cluster-bound traffic routes by hostname, not path (ADR-0002). The UI must never construct raw Ray dashboard URLs; all cluster interaction goes through Mobula control-plane paths (specced in api-v1.md §5.6, §8 below). Per-cluster Ray data is consumed via Mobula's path-based proxy and rendered natively — **no iframes** (see §5.4 and decision D6 in §10).
6. **Fail-closed mirrors backend.** If the backend denies, the UI shows the denial with the required (verb, target) permission and the caller's granted roles (the audit event already carries this; api-v1.md §2.3 puts it in the 403 envelope), not a generic error.
7. **Persistence beats ephemerality.** The core pain point of OSS Ray dashboards is that they die with the head node. This UI's identity is: *history survives clusters* — job history, audit logs, and events live in Mobula's durable store (SQLite today, Postgres per ADR-0004), not in the cluster.

## 2. Personas

Mapped to Mobula's implemented RBAC (`mobula-auth/src/lib.rs`, ADR-0009). The model is **permission-sets, not an ordinal ladder**: four built-in roles, each a set of `(verb, target)` grants where verb ∈ `Read | Write | Delete | Admin` and target ∈ `Job | Cluster` (plus `Service` in the working tree — see below). Identities hold a **set** of roles (union semantics) resolved from IdP group mappings (`RoleMappings`). Enforcement is flat in v0 (a role applies globally); cluster/project-scoped bindings land with the Phase 3 `role_assignments` tables without changing the wire contract.

**Grants matrix** (`Role::grants`, `mobula-auth/src/lib.rs:55`; the `Service` column is uncommitted working-tree state):

| Role | `Target::Cluster` (lifecycle) | `Target::Job` (proxied Ray job surface) | `Target::Service` (Ray Serve) |
|---|---|---|---|
| `Viewer` | Read | Read | Read |
| `Developer` | **Read only** | Read, Write, Delete (submit/stop/delete code) | Read, Write, Delete (deploy = code) |
| `Operator` | Read, Write, Delete (create/patch/terminate) | **Read only** | **Read only** |
| `Admin` | everything | everything | everything |

| Persona | Mobula role(s) | What they do in the UI |
|---|---|---|
| **Platform admin** | `Admin` | Everything: cluster lifecycle, registry management (hostnames, tokens), role mappings, projects/quotas, audit logs. |
| **Cluster operator / SRE** | `Operator` | **Creates, edits, suspends/resumes, terminates clusters** — owns the hardware source of truth. Reads jobs and logs but cannot submit/stop/delete jobs. |
| **ML engineer / developer** | `Developer` | **Submits/stops/deletes jobs**, tails logs, views all clusters — but **cannot create or modify clusters** under the current code (see open question Q9, §10). |
| **Data scientist / viewer** | `Viewer` | Read-only: cluster lists, job status, logs, metrics. All GET/HEAD + websocket log tails. No mutating controls rendered. |
| **Service account** (non-human) | any, via client-credentials | Not a UI persona, but the UI must surface API keys / token-issuance guidance and show service-account activity in audit logs. |

Because identities hold role *sets*, real users will often be `Developer + Operator` (both group mappings match) — the UI must compute each affordance from the union of grants, never from a single "highest role". Note the deliberate split (PLAN review #25/#26): **Operator = lifecycle-but-not-code, Developer = code-but-not-lifecycle**. A user holding only `Developer` sees the cluster console read-only; only `Operator`/`Admin` see create/edit/lifecycle controls.

## 4. Information Architecture

```
/                              Overview dashboard (fleet)
/clusters                      Cluster list (all projects you can see)
  /new                         Create-cluster wizard
  /:clusterId                  Cluster detail
    /overview                  Status, spec vs observed, quick actions
    /nodes                     Node/worker-group view
    /jobs                      Jobs on this cluster (live via gateway)
    /logs                      Aggregated logs (WS tail)
    /metrics                   Metrics (embedded or Grafana deep-link)
    /events                    Cluster event/audit stream
    /config                    Spec editor (YAML/form), registry entry (admin)
/jobs                          Global job history (persistent, cross-cluster)
  /:jobId                      Job detail + logs
/services                      Ray Serve services (API landing in working tree; screen spec pending a future revision)
/registry                      Cluster registry admin (Admin) — hostnames, tokens
/audit                         Audit log viewer (Admin)
/access                        Users, roles, role mappings, service accounts (Admin)
/settings                      Org/project settings, quotas (Phase 3+)
/docs                          (existing) Swagger UI — link, don't rebuild
```

Navigation shell: left sidebar with the sections above; top bar carries **project switcher** (once projects land), **identity/role chip**, and **control-plane health indicator** (`/healthz` + `/api/v1/version`).

## 5. Screen Specifications

Each screen lists: purpose → data backing (with implementation status) → key interactions → role gating.

### 5.1 Overview dashboard `/`

**Purpose:** the fleet at a glance — the screen Ray OSS doesn't have.

- **Backing:** *specced (api-v1.md §5.5, Milestone B), not yet in code* — `GET /api/v1/overview` aggregate. Until it lands: compose from the **implemented** `GET /api/v1/clusters` (state counts, resource totals computable client-side) + per-cluster health probe through the control plane; job-count cards stay hidden (`active_jobs`/`failed_jobs_24h` are `null` until the job-history store exists).
- **Content:**
  - Stat cards: clusters by state (donut chart keyed to the 9 `ClusterState` values), total GPUs/CPUs (summed from `WorkerGroup` replicas × cpu/gpu), active jobs, failed jobs (24h).
  - Cluster table (compact): name, project, state badge, GPU/CPU totals, uptime, age.
  - Recent activity feed: audit events (`subject, cluster, method, path, status, latency_ms` — fields already emitted to `mobula::audit`).
  - Unhealthy panel: `Degraded` clusters, failed jobs, pending jobs older than threshold.
- **Interactions:** click-through to cluster detail; filter by project/state; auto-refresh (polling 15–30s; SSE once the event stream lands, §3.9).
- **Roles:** Viewer+.

### 5.2 Cluster list `/clusters`

- **Backing:** *implemented* — `GET /api/v1/clusters` → `ClusterView[]` (`clusters.rs:109`), mounted when `serve` runs with a store (`--kuberay-namespace`, state in SQLite via `--db` or in-memory otherwise). `ClusterView` carries `id, generation, desired, observed_state, observed_generation, project, ray_version, est_min_hourly, est_max_hourly`; the full `ClusterSpec` and `created_at` are api-v1.md's proposed additive extensions (§8, delta #2). api-v1.md §4 also specifies a Milestone-A registry-backed fallback (`spec: null` = "registered, unmanaged") for deployments without the controller enabled.
- **Content:** table — name, project, state badge, ray_version, image, worker-group summary (`3× gpu:a100 × 2–8 replicas`), TTL, created, actions menu (Suspend / Resume / Terminate per legal transitions — but see §5.4: only terminate exists in code today).
- **Interactions:** sort/filter/search; bulk actions deferred; "New cluster" button (**Operator/Admin only** — see §5.3).
- **Empty state** matters here: first-run with zero clusters should distinguish "Register an existing Ray cluster" (registry entry — unmanaged, job-gateway-only) from "Create a new cluster" (managed, reconciler-backed) — these are different mental models and both must exist.

### 5.3 Create-cluster wizard `/clusters/new`

**The most important form in the product** — this is the "source of truth for hardware" the user asked for. Multi-step wizard mirroring `ClusterSpec` exactly:

1. **Basics** — `name`, `project` (select from permitted projects), labels (planned; not yet in the type — flag as forward-compat).
2. **Head node** — `head_cpu`, `head_memory`.
3. **Worker groups** (repeatable block) — `name`, `cpu`, `memory`, `gpu` (optional, e.g. `"nvidia.com/gpu: 4"` or SKU), `min_replicas`, `max_replicas`, `replicas`. Validation enforces `min ≤ replicas ≤ max` and non-empty name, client-side, mirroring server validation. Explain the ADR-0007 field-ownership rule inline: with autoscaling on, Mobula owns only min/max; the `replicas` field is disabled when autoscaling is enabled.
4. **Runtime** — `ray_version`, `image`, env vars (planned), volumes (planned).
5. **Lifecycle** — `ttl_seconds` (**max-age reaping** as implemented — a Running cluster past `ttl_seconds` is marked Terminated; *idle*-based reaping needs job-activity tracking and is deferred per PLAN Phase 3 slice 4 — the form's copy must say "maximum lifetime", not "idle timeout"), suspend policy (planned — no `DesiredState::Suspended` yet).
6. **Review** — render the exact TOML/JSON spec that will be submitted, with a diff view when editing an existing cluster. **Show the spec as the artifact** — reinforces that Mobula is declarative.

- **Backing:** *implemented* — `POST /api/v1/clusters` (`clusters.rs:158`). Idempotency is **derived**, not client-minted: the reconcile key is `{cluster_uid}/{spec_generation}` (ADR-0007), and POST is an **upsert** — resubmitting after a network failure with an unchanged spec returns the existing generation; a changed spec bumps it. Double-create is impossible by construction, so the wizard is safely resubmittable without any idempotency-key plumbing. Create also enforces **quota admission**: projects with a configured limit get 409 `quota_exceeded` when live max-demand + request exceeds it — render this as a first-class form error with the project's limit/in-use/requested numbers (api-v1.md §2.3).
- **Roles:** **Operator or Admin** (create requires `Write` on `Target::Cluster`; `Developer` has Read-only on clusters under ADR-0009 — this contradicts the original "Developer creates clusters" intent; see open question Q9, §10), within project quota where configured (unconfigured projects are unlimited in v0).

### 5.4 Cluster detail `/clusters/:id`

Tab layout. Header: name, state badge, project, actions (Edit config, Suspend/Resume, Terminate — rendered from `can_transition()`), and a "spec generation N → observed generation M" indicator when they diverge (reconcile in progress — `ClusterView.generation` vs `observed_generation` is exactly this signal).

- **Overview tab:** desired spec card vs observed state card (`observed_state` from the reconcile engine's observation, ADR-0006), head endpoint, gateway hostname, timeline of recent state transitions. *Backing:* `GET /api/v1/clusters/{id}` *implemented* (`clusters.rs:136`) — but note `ClusterView` today omits the full `spec` and `created_at`; api-v1.md §3.4 adds both as additive fields. Until then the spec card renders from the list-page spec only if fetched elsewhere, or shows metadata-only.
- **Actions reality check (backend today):** **Terminate exists** (`DELETE /api/v1/clusters/{id}` sets desired=Terminated, 202). **Suspend/Resume and Edit (PATCH) do not** — `DesiredState` is only `Running | Terminated` (`store.rs:20`); api-v1.md specs `POST …/suspend|resume|terminate` + `PATCH` as Milestone B (delta #3 adds `DesiredState::Suspended`). Render Suspend/Resume/Edit disabled with a "backend pending" note until those land, never hidden silently.
- **Nodes tab:** head node + per-worker-group breakdown; per-node rows (node id, type/group, CPU/GPU alloc, status) sourced from Ray's cluster view *through the control plane*. Node add/remove in Mobula's model = editing worker-group replica bounds (scale is group-level, not node-level — the UI must teach this; there is no "add node" button, there is "edit worker group"). *Backing:* specced (api-v1.md §5.3, `GET /api/v1/clusters/{id}/nodes`), not yet in code.
- **Jobs tab:** live job list for this cluster. The southbound is *implemented* in the gateway (Ray Jobs API passthrough with credential swap), but the browser-consumable path-based proxy (`/api/v1/clusters/:id/jobs…` — api-v1.md §5.6, Milestone C) is not built yet; the UI never constructs cluster host URLs.
- **Logs tab:** streaming log viewer over the websocket bridge (implemented at `gateway.rs`), again via a control-plane WS endpoint (api-v1.md §5.6, southbound-connect-before-upgrade so an unreachable cluster is a clean 502, never a dead socket). Follow/pause, grep, download.
- **Metrics tab:** Phase-dependent — v1 renders key metrics natively (rebuilt views fed by Ray's HTTP API via the control-plane proxy) and/or deep-links out to user-configured Grafana in a new tab; richer native charts land with Mobula §3.9 Prometheus work. Design the panel layout now so charts drop in later without re-layout.
- **Events tab:** per-cluster audit/transition stream (JSONL today, Postgres-backed with pagination Phase 3).
- **Config tab:** read view of the effective spec + registry entry; Admin sees hostname, `api_base_url`, masked token with rotate control; edit opens the wizard pre-filled with a diff review (PATCH per api-v1.md §5.1 — replace semantics, generation bumps only on real change).

### 5.5 Jobs

- **Global history `/jobs`:** cross-cluster, persistent job records (specced: api-v1.md §5.7, `GET /api/v1/jobs` — Postgres-backed, records written by the gateway on submission; **not yet in code** — the gateway does not record job history today). Table: job id, cluster, submitter (from audit `subject`), status (Ray states `PENDING/RUNNING/SUCCEEDED/FAILED/STOPPED` — uppercase, Ray's own strings), duration, submitted-at. This screen is the direct answer to "Ray dashboards forget everything."
- **Job detail:** metadata, entrypoint/command, runtime env, status timeline, log viewer (live tail while running; archived logs after Phase 3 durable capture), stop/delete actions (Developer+).
- **Submit job (D4 — CLI-first):** the UI deliberately does not offer form-based submission in v1. Instead it provides a **command helper**: pick a cluster, optionally paste your existing `ray job submit` command, and the UI outputs the exact command plus the `RAY_JOB_HEADERS` snippet with your token-flow instructions. The UI teaches the CLI path rather than replacing it; a form-based submit surface may be revisited post-v1.

### 5.6 Registry admin `/registry` (Admin)

- **Backing:** *implemented as file* — `ClusterRegistry` TOML (`registry.rs`). The read endpoint `GET /api/v1/registry/clusters` is specced (api-v1.md §5.4, Milestone A, returns `read_only: true, source: "file"`) but **not yet in code** — until it lands this screen has no data source.
- **v1 scope (D5 — read-only):** the screen is **read-only until the dynamic registry lands**. Table of `ClusterEndpoint`s — id, hostname, api_base_url, token status (`token_set` boolean — never the value), last validation result — plus the file path and a "restart required after edit" note. The write API waits because it pulls in the southbound SSRF-hardening open items (CA bundle knob, link-local denylist); no partial write surface ships early. api-v1.md §5.4 specifies the Phase-3 write surface now (`POST/PATCH/DELETE /registry/clusters`) so the form design is settled.
- **Phase 3 add/edit form** (spec now, build later) must mirror the backend validation exactly (`registry.rs`): duplicate hostname/id rejected (case-insensitive), http/https only, no userinfo/fragment, token-over-http blocked unless insecure-transport is allowed. Surface these as inline form errors using the server's `RegistryError` variants mapped to 409/422 codes (api-v1.md §5.4 table), not generic messages.
- **Security affordances:** token field is write-only password input with "replace" semantics; warn when `api_base_url` is plain HTTP.

### 5.7 Audit log viewer `/audit` (Admin)

- **Backing:** *implemented* as JSONL audit target (`mobula::audit` — already carries `subject, cluster, method, path, status, latency_ms`, plus `decision`/`reason` and required/granted on denials); the read endpoint `GET /api/v1/audit` is specced (api-v1.md §5.9, with filters and CSV export) but **not yet in code** — Postgres-backed with filtering in Phase 3.
- **Content:** filterable table (time range, subject, cluster, method, path, status ≥ 400, latency). Include authz denials (they carry required/granted permission — render as first-class "access denied" rows). Export to JSON/CSV.

### 5.8 Access control `/access` (Admin)

- **v1:** read-only view of effective role mappings from `auth.toml` — now **four** mapping lists (`admin`, `operator`, `developer`, `viewer`; `RoleMappings`, `mobula-auth/src/lib.rs:98`) — plus a "who am I" panel showing the caller's `Identity` (subject, email, groups, **roles array**). Editing stays in the config file + restart; the UI shows the file path and documents the flow. Backing endpoints (`GET /api/v1/identity`, `GET /api/v1/access/roles`) are specced (api-v1.md §5.8) but **not yet in code**; api-v1.md also specifies a dev-mode identity (`roles: ["admin"]`) so the unauthenticated dev loop renders the full console.
- **Phase 3+:** editable mappings, scoped `role_assignments` (per-cluster/project bindings to users, service accounts, and groups — ADR-0009), custom roles, service account management.

### 5.9 Settings / quotas (Phase 3+)

Project list, per-project quota editors (CPU/GPU/instance caps), price-sheet upload for cost views (Phase 4). Placeholder in IA now so navigation doesn't churn later. **Backend status:** quota *enforcement* on cluster create and price-sheet *estimation* are implemented (Phase 4 slice 1, `mobula-policy` + `PolicyConfig` — configured via serve options, no config file or management API yet); the management endpoints for editing quotas/price sheets are greenfield.

### 5.10 Auth & shell flows

- Web login is **Authorization Code + PKCE** against the configured OIDC issuer (REQUIREMENTS §3.6) — **still not implemented backend-side**; api-v1.md §5.11 sketches the four endpoints (login/callback/refresh/logout) and flags token custody (cookie session vs in-memory + IdP refresh) as an open question. The UI is blocked on this and it's on the critical path for Milestone B. Dev mode uses `--dev-allow-unauthenticated`.
- 401 → redirect to login; 403 → rendered denial page showing required (verb, target) vs granted roles — api-v1.md §2.3 makes the 403 a structured envelope carrying exactly this data (today it's bare text; delta #1).
- Session expiry → silent refresh if IdP supports it, else re-login with deep-link return.

## 6. Component & Interaction Specs (cross-cutting)

- **State badge:** one component, 9 variants + tooltip ("Suspended → resuming reprovisions the cluster; there is no fast path to Running"). Colors: Running=green, Degraded=amber, Terminating/Suspending/Provisioning/Updating=animated blue, Pending=grey, Suspended=grey-outline, Terminated=muted.
- **Spec-vs-observed diff:** two-column renderer used on cluster detail, wizard review, and edit flows.
- **Log viewer:** virtualized scrolling, websocket with backpressure, reconnect with exponential backoff, "connection lost" banner (WS bridge has no idle limits yet — design for drops).
- **Async action pattern:** lifecycle actions (create/suspend/terminate) are long-running → optimistic transition to the intermediate state, then poll/SSE until observed state settles; failure restores the action and shows the provisioner error.
- **Destructive confirmations:** Terminate requires typing the cluster name; the dialog states that Terminated is terminal.
- **Time/refresh:** all timestamps relative-with-absolute-tooltip; lists poll at 15–30s, detail pages 5–15s, log tails realtime.
- **Empty/error states:** every list has first-run, no-results, backend-unreachable (502 from gateway = "cluster unreachable"), and permission-denied variants.

## 9. Phasing Plan (UI aligned to Mobula's phases)

Re-baselined 2026-08-15: Mobula has completed Phases 1–3 and Phase 4 slice 1. Much of what this plan assigned to "Phase 3 co-design" **already exists in code**; the milestones below are re-scoped accordingly, and they align 1:1 with api-v1.md §9's implementation checklist (same letter codes).

**Milestone A — Foundation (unblocked today):** repo scaffolding, design system, shell, login (dev-mode), generated API types **from the committed `openapi.json`**, `/docs` link. Screens: **Cluster list + Cluster detail reading the *implemented* store-backed endpoints** (the earlier "read endpoints don't exist yet" assumption is stale — they do), Registry admin + Identity panel once their Milestone-A endpoints land (api-v1.md §4: three small endpoints, no persistence needed), health indicator. Delivers a usable read-mostly console against current Mobula — including real create/terminate if run against a controller-enabled backend.

**Milestone B — Hardware management (backend ~70% done):** create/edit wizard, lifecycle actions, spec-vs-observed, nodes tab, audit viewer. Backend remaining: `PATCH`, `DesiredState::Suspended` + suspend/resume/terminate action endpoints, `ClusterView` ✱ fields, structured 403 envelope, `GET /overview|audit|access/roles`, Postgres store (SQL already ports), PKCE auth. UI-side, this is the "source of truth for hardware" milestone: wizard, diff review, async-action pattern, quota-exceeded form errors — all against endpoints that mostly exist today.

**Milestone C — Workloads:** jobs tab via the path-based control-plane proxy (southbound already implemented in the gateway), WS log tails, global job history (needs gateway-side history capture + Postgres), nodes aggregation, projects + quotas *management* UI (quota enforcement itself is already live on create).

**Milestone D — Parity push (Phase 4):** metrics native, events SSE, scheduled jobs, **services/Ray Serve UI** (the CRUD API is already in the working tree — list/detail/deploy flows against `Target::Service`, Developer-writable), notifications, usage/cost dashboards (per-cluster `est_*_hourly` cost fields already flow through `ClusterView` — the UI surfaces them when non-null), images.

**Post-v1:** workspaces, SCIM, fair-share, custom roles.

## 10. Decisions & Open Questions

**Decided:**

1. ~~Tech stack confirmation~~ **DECIDED (D1): React + TypeScript + Vite** (§7).
2. ~~Node-level vs group-level management~~ **DECIDED (D2): group-level semantics.** Mobula's model manages worker-group replica bounds, not individual nodes; the UI teaches "edit worker group" rather than simulating per-node add/remove. Per-node views are observability-only (nodes tab).
3. ~~Metrics strategy for v1~~ **DECIDED (D3): blanket no-iframe policy, Grafana included.** v1 = native Ray-API metric views + new-tab deep-links to user-managed Grafana; native charts when Mobula's Prometheus work (§3.9) lands.
4. ~~Job submission surface~~ **DECIDED (D4): CLI-first.** The UI ships a `ray job submit` + `RAY_JOB_HEADERS` command helper and focuses on observability; no form-based submission in v1 (§5.5).
5. ~~Registry editing in v1~~ **DECIDED (D5): read-only until the dynamic registry lands.** Edits stay in `clusters.toml` + restart; the write API (specced in api-v1.md §5.4) waits for the dynamic-registry work and its southbound SSRF hardening (§5.6). Phase 3 shipped without the dynamic registry, so this decision still binds.
6. ~~Embedded Ray dashboard~~ **DECIDED (D6): no iframes; rebuild selected Ray dashboard views natively.** Rationale: (a) Ray's dashboard has no authentication, and an iframe navigation cannot carry the `Authorization: Bearer` header Mobula's security model requires — supporting it would mean adding cookie sessions to the gateway just for browsers, punching a hole in the JWT-terminates-at-Mobula design; (b) iframed dashboards die with the head node, resurrecting the ephemerality problem this product exists to fix; (c) Ray's dashboard is an open-source React SPA over plain HTTP APIs on `:8265`, so rebuilding the needed subset (node/worker hierarchy, job list/detail, log viewer, Serve app list, events) means calling the same endpoints through Mobula's control-plane proxy — the auth story stays intact; (d) the expensive views (CPU flame graphs, Perfetto task timelines, stack-trace profiling) are explicitly out of scope for v1 — link out to the cluster's own dashboard for those, in a new tab, behind the identity proxy when it exists.

**Still open:**

7. **Design language/branding** — any existing Mobula/Nebari brand constraints, dark/light mode requirements?
8. **Package/embed mechanics** — confirm rust-embed-style single-binary serving is the target (affects build pipeline design).
9. **Should the UI let Developers create clusters?** *(product conflict, surfaced by the re-baseline)* This spec's original persona model had Developers creating clusters "from permitted configs" (§2/§5.3 pre-v0.2). The backend's ADR-0009 permission-set model grants `Write` on `Target::Cluster` to **Operator/Admin only**; `Developer` is deliberately code-but-not-lifecycle (`mobula-auth/src/lib.rs:64-65`), and api-v1.md follows the code (its §2.2 delta note, §8 item 5). The UI currently gates cluster create/lifecycle on Operator/Admin per the code. If the product decision is that Developers should create clusters (e.g. within project quota — admission control already exists to bound it), that is an RBAC change in `mobula-auth` (`Role::grants`), not an API or UI change; the wizard, error shapes, and gating logic above are unaffected either way. **Undecided — needs product call.**
10. **PKCE token custody** *(from api-v1.md §8 item 6)* — cookie session vs in-memory token + IdP refresh for browser login. §7 leans in-memory; api-v1.md §5.11 is custody-agnostic. Resolve before Milestone B.
